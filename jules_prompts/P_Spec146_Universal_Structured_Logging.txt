[Task / Spec 146: Universal Leveled & Structured Logging Engine with Deep Debugging & Dual Error Handling]

Objective:
Implement Spec 146 (`specs/146-universal-structured-logging/spec.md`) and Task 146 (`specs/146-universal-structured-logging/task.md`) across `paperpilot-gateway`, `paperpilot-cli`, `paperpilot-mcp`, and `paperpilot-pdf`.
Provide:
1. Multi-format logging: `LOG_FORMAT=json|compact|pretty|text` and dynamic log levels via `RUST_LOG` and CLI flags.
2. The Dual Error Model: Log root cause and error chain on the server (`tracing::error!`), while returning a clean, safe structured error with matching `request_id` to the caller.
3. Deep `DEBUG` visibility: Emits clear chronological timelines of inputs, parameters, and step transitions.
4. Stdio isolation: 100% stderr routing for CLI and MCP to protect binary output and JSON-RPC wire frames.

---

### 🚨 Critical Guardrails & Production Rules:

1. **System Resource Constraint**:
   ALWAYS run all cargo tests and builds with memory-safe `-j 4` (e.g. `cargo test -p paperpilot-gateway -j 4`).

2. **The Dual Error Paradigm**:
   Never discard or quietly wrap an error without emitting `tracing::error!` with the root cause and error source chain (`err.source()`). Always correlate with `request_id`.

3. **MCP Stdio Protocol Protection**:
   In `paperpilot-mcp`, the MCP server uses `stdout` strictly for JSON-RPC messages. Under NO circumstances should application logs be written to `stdout`. All `tracing_subscriber` writers in `paperpilot-mcp` MUST be directed explicitly to `std::io::stderr`.

4. **Zero PII & Secret Redaction**:
   Never log raw document contents, decrypted text, or user passwords in log statements or JSON attributes. If passwords are provided in tool inputs, redact to `password="[REDACTED]"`.

5. **🚨 CRITICAL CLI 'watch' SUBCOMMAND GUARD (DO NOT BREAK EXISTING TESTS)**:
   In `paperpilot-cli/src/lib.rs`, do NOT execute `let cli = Cli::parse();` before the `if args.len() > 1 && args[1] == "watch"` check!
   The hot-folder watcher daemon intercepts raw `args[1] == "watch"` directly from `std::env::args()`. `watch` is NOT a Clap subcommand in `Cli`.
   If you call `Cli::parse()` before checking `args[1] == "watch"`, Clap will terminate execution with `error: unrecognized subcommand 'watch'` and break `tests/test_dynamic_naming.rs`!
   Instead:
   - Check `args[1] == "watch"` FIRST.
   - If `args[1] == "watch"`, run the watch loop as before.
   - If not `watch`, parse `Cli::parse()` and initialize `tracing_subscriber` directed to `std::io::stderr`.

6. **Complete All Crates (Do not just add Cargo.toml dependencies)**:
   You must implement the actual Rust code in `paperpilot-mcp/src/main.rs`, `paperpilot-mcp/src/server.rs`, and `paperpilot-pdf/src/operations/`. Do not leave them as unmodified source files.

### Step-by-Step Implementation Details:

#### Step 1: Axum HTTP Tracing Middleware & Request Correlation in `paperpilot-gateway`
1. Ensure `paperpilot-gateway/Cargo.toml` includes:
   ```toml
   tracing = "0.1.44"
   tracing-subscriber = { version = "0.3", features = ["env-filter", "json"] }
   ```
2. In `paperpilot-gateway/src/main.rs`:
   - Inspect `LOG_FORMAT` environment variable (`json`, `compact`, `pretty`, `text`). Default to `text`.
   - Configure `tracing_subscriber::fmt()` with `.with_env_filter(...)` and appropriate formatter (`.json()`, `.compact()`, `.pretty()`, or standard).
3. In `paperpilot-gateway/src/server.rs`:
   - Add Axum middleware `request_id_and_tracing_middleware` that captures or generates a UUID v4 `request_id` (supporting incoming `X-Request-ID`).
   - Create a tracing span containing `request_id`, `http.method`, `http.route`, and `client.ip`.
   - On request start, emit `tracing::debug!(request_id, tool_id, content_len, "Incoming request started")`.
   - On request completion, emit `tracing::info!(request_id, status_code, duration_ms, "Request completed")`.
4. In `paperpilot-gateway/src/handlers.rs`:
   - On handler failure:
     - Emit `tracing::error!(request_id, tool_id, error = %err, "Handler returned error")`.
     - Return HTTP JSON error body: `{"success": false, "error": "...", "code": "...", "request_id": req_id}` and header `X-Request-ID`.

#### Step 3: MCP Protocol Stdio Isolation in `paperpilot-mcp`
1. In `paperpilot-mcp/Cargo.toml`:
   ```toml
   tracing = "0.1.44"
   tracing-subscriber = { version = "0.3", features = ["env-filter", "json"] }
   ```
2. In `paperpilot-mcp/src/main.rs`:
   - Initialize `tracing_subscriber` directed strictly to `std::io::stderr`:
     ```rust
     let log_format = std::env::var("LOG_FORMAT").unwrap_or_else(|_| "text".to_string()).to_lowercase();
     let filter = tracing_subscriber::EnvFilter::try_from_default_env()
         .unwrap_or_else(|_| tracing_subscriber::EnvFilter::new("info"));

     if log_format == "json" {
         let _ = tracing_subscriber::fmt()
             .json()
             .with_writer(std::io::stderr)
             .with_env_filter(filter)
             .try_init();
     } else {
         let _ = tracing_subscriber::fmt()
             .with_writer(std::io::stderr)
             .with_env_filter(filter)
             .try_init();
     }
     ```
3. In `paperpilot-mcp/src/server.rs`:
   - In `execute_call_tool`:
     - On tool dispatch: `tracing::debug!(tool = %name, "Executing MCP tool")`.
     - On tool failure: `tracing::error!(tool = %name, error = %err, "MCP tool execution failed")`.
   - Verify that running `paperpilot-mcp` emits JSON-RPC envelopes strictly on `stdout`.
