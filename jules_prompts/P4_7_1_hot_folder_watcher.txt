[Task 4.7.1 / Spec 139: Headless Hot Folder Watcher Daemon — Full 5-Interface Implementation]

Objective:
Implement Spec 139 (`specs/139-hot-folder-watcher-daemon/spec.md`) which covers ALL required interface wrappers for the Hot Folder Watcher daemon under PaperPilot's Single Core Runner + 5 Wrappers architecture:
  1. CLI (`paperpilot-cli`) — fix and complete `paperpilot watch`
  2. REST Gateway (`paperpilot-gateway`) — new automation endpoints
  3. MCP (`paperpilot-mcp`) — 4 new tools: `watcher_start`, `watcher_stop`, `watcher_list`, `recipe_run`
  4. Desktop UI — via Spec 140 (NOT in scope here; skip)
  5. WASM — Exempt (filesystem watch cannot run in browser sandbox; skip)

Critical Constraints & Guardrails:
1. Always compile and test with `-j 2` (`cargo test -p paperpilot-cli -j 2`, `cargo test -p paperpilot-gateway -j 2`, etc.)
2. Real Tests Only: Zero mock data. Use real PDF fixtures from `fixtures/` or synthetic Lopdf byte buffers.
3. Do NOT break existing CLI commands, gateway endpoints, or MCP tools.
4. The daemon MUST NEVER panic or exit on a corrupted/locked PDF. All errors caught and routed to quarantine.
5. Shared `WatcherRegistry` (`Arc<Mutex<WatcherRegistry>>`) must be passed to BOTH the gateway router and MCP server at startup so they share state.

### PART 1: CLI — `paperpilot-cli`

#### Step 1: Update `WatchCli` args in `paperpilot-cli/src/lib.rs`

Update `WatchCli` struct to use named `--dir` flag instead of positional, and add `--error-dir` and `--once`:

```rust
#[derive(Parser, Debug)]
#[command(name = "paperpilot watch")]
pub struct WatchCli {
    /// Directory to monitor for incoming PDF files
    #[arg(short = 'd', long)]
    pub directory: PathBuf,

    /// Path to .ppflow TOML or JSON recipe to execute per file
    #[arg(short = 'r', long)]
    pub recipe: Option<PathBuf>,

    /// Output directory for successfully processed PDFs
    #[arg(short = 'o', long)]
    pub output: Option<PathBuf>,

    /// Directory to move successfully processed originals (optional)
    #[arg(long)]
    pub move_original: Option<PathBuf>,

    /// Directory to quarantine failed files (default: <dir>/.error)
    #[arg(long)]
    pub error_dir: Option<PathBuf>,

    /// Milliseconds of filesystem inactivity before a file is considered ready
    #[arg(long, default_value_t = 500)]
    pub settle_delay_ms: u64,

    /// Optional webhook URL to POST execution receipt
    #[arg(long)]
    pub webhook: Option<String>,

    /// Process existing files and exit (useful for one-shot batch and testing)
    #[arg(long)]
    pub once: bool,
}
```

#### Step 2: Fix `execute_operation` in `paperpilot-cli/src/commands/watch.rs`

Replace the stub recipe execution with the real unified workflow runner:

```rust
use paperpilot_core::workflow::WorkflowRecipe;
use paperpilot_pdf::operations::workflow::run_workflow;

fn execute_recipe(
    file_path: &Path,
    recipe_path: &Path,
    output_dir: &Option<PathBuf>,
) -> OperationResult<Vec<u8>> {
    // Load recipe from disk (.ppflow TOML or JSON)
    let recipe_str = std::fs::read_to_string(recipe_path)
        .map_err(|e| PdfError::IoError(e))?;
    let recipe: WorkflowRecipe = WorkflowRecipe::from_str(&recipe_str)
        .map_err(|e| PdfError::InvalidInput(e.to_string()))?;

    // Read input PDF bytes
    let input_bytes = std::fs::read(file_path)
        .map_err(|e| PdfError::IoError(e))?;

    // Execute through unified runner
    run_workflow(&recipe, &input_bytes, &Default::default())
}
```

#### Step 3: Initial Sweep + Debounced Queue in `handle_watch`

Before entering the event loop, read all existing `.pdf` files and enqueue them first. Ignore subdirectories like `.error/`, `processed/`, or the output_dir itself. Process existing files sequentially, then switch to event-driven mode (unless `--once` is set, in which case exit after the initial sweep).

#### Step 4: Quarantine & Execution Receipts

On processing failure:
- Create `<dir>/.error/` (or `--error-dir`).
- Move the failing PDF into the error folder.
- Write a companion `{stem}_receipt.json`:
```json
{
  "timestamp": "2026-10-28T17:00:00Z",
  "file": "corrupt.pdf",
  "sha256": "abc123...",
  "success": false,
  "error": "Failed to parse xref table"
}
```

On success, if `--move-original` specified, move source PDF to that dir.

### PART 2: REST Gateway — `paperpilot-gateway`

#### Step 6: Add `WatcherRegistry` to gateway state

In `paperpilot-gateway/src/server.rs`, define:

```rust
use std::sync::Arc;
use tokio::sync::Mutex;
use std::collections::HashMap;
use tokio_util::sync::CancellationToken;

pub struct WatcherHandle {
    pub watcher_id: String,
    pub dir: PathBuf,
    pub recipe: PathBuf,
    pub cancel: CancellationToken,
    pub last_processed_file: Option<String>,
    pub last_processed_at: Option<String>,
    pub total_processed: u64,
}

pub type WatcherRegistry = Arc<Mutex<HashMap<String, WatcherHandle>>>;
```

Inject into Axum app state: `Arc<WatcherRegistry>`.

#### Step 7: Add 4 automation route handlers in `paperpilot-gateway/src/handlers.rs`

```rust
// POST /v1/automation/watchers
// Body: { dir, recipe, output_dir?, error_dir?, settle_delay_ms?, move_original? }
// Action: Spawn tokio task running handle_watch(), store CancellationToken in registry
// Response 201: { watcher_id, status: "watching", dir, recipe }

// GET /v1/automation/watchers
// Action: Read registry, return list of all WatcherHandle summaries
// Response 200: { watchers: [...] }

// DELETE /v1/automation/watchers/:watcher_id
// Action: Look up registry, call cancel.cancel(), remove entry
// Response 204: No content

// POST /v1/automation/run
// Body: multipart/form-data (file: bytes, recipe: TOML text)
// Action: Run recipe against uploaded bytes in-memory via run_workflow()
// Response 200: { success, output_bytes (base64), receipt: { job_id, duration_ms, stages } }
```

Register routes in `server.rs`:
```rust
.route("/v1/automation/watchers", post(start_watcher).get(list_watchers))
.route("/v1/automation/watchers/:id", delete(stop_watcher))
.route("/v1/automation/run", post(run_recipe_once))
```

### PART 3: MCP Tools — `paperpilot-mcp`

#### Step 9: Register 4 new MCP tools

In `paperpilot-mcp/src/` (follow the exact same registration pattern used by existing tools):

**Tool: `watcher_start`**
- Input: `{ dir: string, recipe: string, output_dir?: string, settle_delay_ms?: integer }`
- Action: Starts watcher via shared `WatcherRegistry` (same Arc as gateway).
- Returns: `{ watcher_id: string, status: "watching" }`

**Tool: `watcher_stop`**
- Input: `{ watcher_id: string }`
- Action: Cancels the watcher task via `CancellationToken`.
- Returns: `{ success: true }`

**Tool: `watcher_list`**
- Input: `{}` (none)
- Returns: `{ watchers: [{ watcher_id, dir, recipe, status, last_processed_file, total_processed }] }`

**Tool: `recipe_run`**
- Input: `{ input: string, recipe: string, output: string }`
- Action: One-shot `run_workflow()` call. No daemon spawned.
- Returns: `{ success: bool, output: string, receipt: { stages: [...] } }`

- `test_mcp_watcher_start_stop`: Call `watcher_start`, verify returns `watcher_id`. Call `watcher_stop`, verify success.
- `test_mcp_watcher_list`: Start two watchers, call `watcher_list`, assert both appear.
- `test_mcp_recipe_run`: Call `recipe_run` with real fixture PDF and a 2-step recipe TOML, assert output PDF written and receipt has 2 stages.
