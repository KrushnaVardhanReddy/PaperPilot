Task: Phase E.4 — Overall System Performance & Latency Benchmarking

Hey Jules! We need to prove that PaperPilot is blazing fast even under the heaviest real-world loads. Build a comprehensive, automated benchmarking suite that produces hard numbers across every layer of the system.

---

## Step 1: Fixture Generation

Programmatically generate the following test PDF fixtures in `tests/bench_fixtures/` (do NOT commit them — add to `.gitignore`):

| Fixture | Description |
|---|---|
| `tiny_1page.pdf` | 1 page, text-only |
| `small_10page.pdf` | 10 pages, text + embedded image per page |
| `medium_50page.pdf` | 50 pages, realistic content (tables, headings, body text) |
| `large_100page.pdf` | 100 pages, mixed content |
| `xlarge_500page.pdf` | 500 pages, text-heavy (simulate a legal contract or book) |
| `batch/doc_001.pdf`–`doc_020.pdf` | 20 individual 5-page PDFs for batch/merge tests |

Use the `paperpilot-cli create` command or `lopdf`/`printpdf` directly in Rust to generate these.

---

## Step 2: Core Operations — Scaling Curve Benchmarks

Use **Rust `criterion`** for all Rust benchmarks (add `criterion` to `paperpilot-core/Cargo.toml` under `[dev-dependencies]`). For each operation below, benchmark it across ALL fixture sizes (1, 10, 50, 100, 500 pages) to produce a proper scaling curve:

### Operations to Benchmark
1. **Merge** — Merge the 20 batch PDFs into one 100-page document
2. **Split** — Split the 100-page document into individual pages
3. **Extract Text** — Extract all text from each fixture size
4. **Compress** — Apply lossless compression to each fixture size
5. **Watermark** — Apply a text watermark to every page
6. **Encrypt** — Encrypt with AES-256 across each fixture size
7. **OCR** — Run OCR on the `large_100page.pdf` (this is the most CPU-intensive operation; treat it separately as it may take longer)
8. **PDF → Image** — Convert each page of `medium_50page.pdf` to PNG (per-page rendering cost)

### Metrics Required per Operation
- **P50 / P95 / P99 latency** (criterion gives these automatically)
- **Throughput** — pages per second
- **Peak memory (RSS)** — use `/proc/self/status` on Linux or the `sysinfo` crate

---

## Step 3: Cold Start vs Warm Start

Measure the overhead of the **first invocation** versus subsequent ones for Merge and Extract Text on `large_100page.pdf`:
- Run the operation **once** — record as "cold start" time
- Run it **10 more times** — average as "warm" time
- Report the delta

---

## Step 4: Memory Leak Detection

For Merge and Extract Text, run each operation **1000 times** in a tight loop. After every 100 iterations, sample RSS memory. Output a small table showing if memory grows over time (potential leak) or stays flat (clean).

---

## Step 5: Concurrent Operations Benchmark

Simulate a real desktop user doing multiple things at once. Using `std::thread::spawn` or `tokio::spawn` (whichever matches the codebase), run these 4 operations simultaneously on separate threads:
- Thread A: Merge 20 batch PDFs
- Thread B: Extract text from `large_100page.pdf`
- Thread C: Compress `medium_50page.pdf`
- Thread D: Watermark `small_10page.pdf`

Measure **total wall-clock time** and compare to sequential time to show parallelism speedup.

---

## Step 6: NLP Layer — High-Throughput Query Benchmark

Using the `OfflineNlpResolver` in `paperpilot-nlp`, run **10,000 queries** (not just 1,000) through the resolver. Vary query complexity:
- 50 simple single-word commands ("merge", "split")
- 50 medium natural-language phrases ("please compress this report.pdf")
- 50 complex sentences ("Extract pages 3-7 from the Q3 report and save to output.pdf with password 'abc123'")

Repeat each set ~67 times to reach 10,000 total. Report:
- **Average latency per query (µs, should be <500µs)**
- **P99 latency (µs)**
- **Total throughput (queries/second)**
